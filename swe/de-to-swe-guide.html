FastAPI Auth API Design Patterns

From DE to SWE

A guided tour through the Data API codebase

Who this is for: A senior Data Engineer who knows Python well and wants to understand how production FastAPI services are designed and wired together. All examples are pulled from real code in this repo.

How long: A focused day or two. Each section is self-contained — read in order the first time, use as a reference after.

1The Big Picture

Before diving into code, here's what happens when a client hits POST /api/v3/data/list:

HTTP Request → FastAPI router matches the path web/api/router.py → Dependency injection resolves auth web/api/auth.py → Route handler runs web/api/v3/data/views.py → Converts API request → RetrieverInput → RetrieverFactory.fetch_single() retriever/RetrieverFactory.py → Looks up which retriever handles these data items (DB lookup) → Checks permissions → Instantiates the right retriever (e.g. IntelDataRetriever) → Calls retriever.fetch() retriever/intel_data_retriever/ → Queries the database → Returns rows → Converts RetrieverOutput → APIResponse → FastAPI serializes response model → JSON

Each arrow is a layer you'll understand by the end of this guide.

2FastAPI Fundamentals

Defining Routes

FastAPI routes are Python functions decorated with HTTP method decorators. The framework parses JSON bodies, validates types, and serializes responses automatically.

web/api/v3/data/views.py

from fastapi import APIRouter

router = APIRouter()

@router.post(
    "/v3/data/list",
    response_model=APIResponse,           # FastAPI validates + serializes the return value
    description="V3 Data API with row-based pagination...",
    openapi_extra={"x-sdk-include": True},  # Custom metadata for SDK generation
)
async def get_data_v3(
    data_request: V3APIRequest,           # Body — FastAPI deserializes + validates via Pydantic
    auth_ctx: AuthContext = Depends(resolve_auth),  # Injected dependency (more below)
) -> APIResponse:
    ...
    return api_results

What FastAPI is doing for you:

  • Reads the JSON body → calls V3APIRequest(**body_dict) → raises 422 if validation fails
  • Calls resolve_auth() and passes the result as auth_ctx
  • Takes your return value, calls APIResponse(**return_value), serializes to JSON
  • Generates OpenAPI docs at /api/docs automatically from the type hints

DE Analogy

Think of it like a stored procedure signature — you declare input/output types and the framework handles the plumbing.

Async Handlers

Every handler in this codebase is async def because all the expensive work (DB queries, HTTP calls to the auth service) is I/O-bound.

# Synchronous — blocks the thread while waiting for DB
def get_data(request):
    result = db.query(...)   # thread sits idle here
    return result

# Asynchronous — releases the thread while waiting, handles other requests
async def get_data(request):
    result = await db.query(...)   # yields control, resumes when DB responds
    return result

The practical rule: If a function does I/O (DB, HTTP, Redis), it must be async def and you await it. If it's pure computation, def is fine.

Watch out

Calling time.sleep() inside an async handler freezes the entire service. Use await asyncio.sleep() instead. FastAPI runs async handlers on a single event loop — blocking it blocks every concurrent request.

DE Analogy

Same concept as non-blocking I/O in Spark or async reading in Pandas. The process doesn't block waiting for data to arrive.

Pydantic v2 Models

Pydantic is the validation layer. Every request body and response is a Pydantic model — a Python class that declares field types and validates them at instantiation.

web/api/v3/data/schema.py

from pydantic import Field
from data_api.web.api.v2.data.schema import APIRequest

class V3APIRequest(APIRequest):         # Inherits ids, data_item_names, page_token, filters, sort
    page_size: int = Field(
        100,                            # default value
        ge=1,                           # validation: must be >= 1
        description="Number of rows to retrieve per page.",
    )
    params: dict[str, Any] | None = None   # Optional dict for dataset-specific params

The parent APIRequest looks like this:

class APIRequest(BaseModel):
    ids: list[APIIdentifier] | None = None
    data_item_ids: list[int] | None = None
    data_item_names: list[str] | None = None
    page_size: int = Field(1000, ge=1)
    page_token: str | None = None
    sort: Sort | None = None
    filters: FilterGroup | None = None

Key Pydantic behaviors to know:

  • Fields with no default are required — FastAPI returns 422 if they're missing
  • X | None = None makes a field optional with a None default
  • Field(default, ge=1, le=10000) adds validation constraints
  • Pydantic v2 is strict about types — "100" will not silently coerce to 100 unless configured
  • Inheritance works exactly as expected: V3APIRequest has all fields of APIRequest plus params

Dependency Injection

This is FastAPI's most important concept. Depends() lets you declare that a handler needs a resolved value — FastAPI calls the dependency function and passes the result automatically.

# The dependency — resolves auth, returns an AuthContext
async def resolve_auth(
    request: Request,
    _credentials: HTTPAuthorizationCredentials | None = Depends(_bearer_scheme),
) -> AuthContext:
    # ... validates the Bearer token, returns an AuthContext dataclass
    return ctx

# The handler — receives the already-resolved AuthContext
async def get_data_v3(
    data_request: V3APIRequest,
    auth_ctx: AuthContext = Depends(resolve_auth),  # FastAPI calls resolve_auth, injects result
) -> APIResponse:
    ...

Dependencies can themselves depend on other things. FastAPI builds a full dependency graph and resolves it top-down:

get_data_v3 └── resolve_auth (validates Bearer token) └── _bearer_scheme (extracts the token string from headers)

DE Analogy

Think of it like a task DAG in Airflow — each dependency is a node, FastAPI resolves them in order, and the final function only runs when all upstream nodes are satisfied. If any node raises an exception, the chain short-circuits and returns an error response.

Benefit for testing: In tests you can override a dependency to return a fake AuthContext without touching any real auth logic. The endpoint handler doesn't care where its auth_ctx came from.

3Auth

Authentication vs Authorization

These are two different questions that DAPI handles at different layers:

ConceptQuestion it answersWhere in DAPI
AuthenticationIs this token valid? Was it issued by Octus Auth? Has it expired?auth.py → resolve_auth()
AuthorizationEven if valid, is this user allowed to access this specific data?RetrieverFactory → validate_permissions() and data item status checks

JWT Validation

Every token is a JWT (JSON Web Token) — a signed, base64-encoded blob containing claims: user ID, role, features, product grants, etc.

web/api/auth.py

auth = OctusAuth(issuer=settings.auth_issuer)   # initialized once at module load

async def resolve_auth(request: Request, ...) -> AuthContext:
    token = auth_header[len("Bearer "):]
    result = await auth.validate_token_async(token)   # calls the Octus auth SDK

    if not result.is_valid:
        raise UnauthorizedException("Invalid bearer token")

    # If valid, extract claims from the principal
    ctx.principal = result.principal
    ctx.application_id = result.principal.get_application_id()
    ctx.features = _parse_int_claims(result.principal.get_features())
    ctx.product_grants = _parse_int_claims(result.principal.get_product_grants())

The OctusAuth SDK handles the cryptographic verification — checking the token's signature against the issuer's public keys. If the token was tampered with, expired, or issued by a different service, result.is_valid is False.

What's inside a JWT claim in this system:

  • role: User | ClientApi | ServiceApp | ServiceAsUser | Agent
  • sub: user ID
  • email: user's email
  • application_id: service ID (for ServiceApp/ServiceAsUser tokens)
  • features: list of feature flag IDs the user has
  • product_grants: list of product access IDs the user has

Token Roles and the is_public Flag

# data_api/web/api/auth.py

PUBLIC_ROLES = ("User", "ClientApi")
INTERNAL_ROLES = ("ServiceApp", "ServiceAsUser", "Agent")

# During resolve_auth:
role = result.principal.get_role()
ctx.is_public = role in PUBLIC_ROLES   # True for external clients, False for internal services
Token RoleIssued tois_publicINTERNAL_EXTERNAL fieldsINTERNAL fields
UserEnd users✓ True✓✗
ClientApiExternal API consumers✓ True✓✗
ServiceAppInternal services✗ False✓✓
ServiceAsUserInternal service + user context✗ False✓✓
AgentAdmin impersonation✗ False✓✓

The is_public flag flows through the entire request — from auth → retriever input → DB query — determining which data items come back in the response.

Dependency Chain

Three levels of auth restriction are built by chaining dependencies on top of each other:

resolve_auth → optional, no error if no token └── resolve_auth_required → must have a valid token (any role) └── resolve_user_id → must be a User token specifically
# Level 1: Optional — returns empty AuthContext if no token
async def resolve_auth(request, _credentials=Depends(_bearer_scheme)) -> AuthContext:
    ctx = AuthContext()
    if token_present:
        result = await auth.validate_token_async(token)
        if result.is_valid:
            ctx.principal = result.principal
            # ... populate ctx
    return ctx   # returns even with no token

# Level 2: Requires any valid token
async def resolve_auth_required(
    auth_ctx: AuthContext = Depends(resolve_auth)
) -> AuthContext:
    if auth_ctx.principal is None:
        raise DataApiException(status_code=401, message="Authentication required")
    return auth_ctx

# Level 3: Requires specifically a User token (not a service token)
async def resolve_user_id(
    auth_ctx: AuthContext = Depends(resolve_auth_required)
) -> str:
    if auth_ctx.principal.get_role() != "User":
        raise DataApiException(status_code=401, message="Must pass user token")
    return auth_ctx.principal.get_user_id()

Which endpoints use which:

EndpointAuth dependencyWhy
POST /v3/data/listresolve_authBoth public and internal can query; no token required
POST /v2/file-uploadresolve_user_idOnly human users can upload, not automated services
POST /v1/data/deleteresolve_user_idDestructive action — must be a real user, auditable

How Auth Context Flows Downstream

The AuthContext object is passed down through the stack so retrievers and DB queries can make access decisions:

web/api/v3/data/views.py

async def get_data_v3(data_request, auth_ctx=Depends(resolve_auth)):
    set_auth_context_vars(auth_ctx)    # writes to Python context vars (async thread-local equivalent)
    ...
    retriever_request = await v3_api_request_to_retriever_input(
        data_request,
        retriever_factory,
        auth_ctx,                      # auth_ctx passed into retriever input
    )

At the retriever level, each retriever can enforce its own permission rules:

retriever/intel_data_retriever/intel_data_retriever.py

async def validate_permissions(self, permissions: Permissions) -> None:
    if not permissions.product_grants:
        raise NoProductGrants(
            "You are not permissioned to access intel data."
        )
    if (
        permissions.is_public_request
        and ProductGrant.INTEL_DATA.value not in permissions.product_grants
    ):
        raise NoProductGrants(
            "You are not permissioned to access intel data."
        )

The product_grants value here originated as a claim in the JWT → extracted in resolve_auth() → stored on AuthContext → passed as RetrieverInput → arrives here.

DE Analogy

Row-level security in a data warehouse. The same query runs for everyone, but a filter is applied based on who's asking. Here it's enforced at the application layer instead of the DB layer, but the concept is identical.

Authorization: SYSTEM Data Items

Beyond role-based checks, some data items are SYSTEM status. Even a valid internal token can't access them unless the calling application has been explicitly allowlisted:

retriever/RetrieverFactory.py

async def _validate_system_data_item_access(self, data_item_ids):
    application_id = application_id_ctx_var.get()

    # No application_id at all → can't access SYSTEM items
    if not application_id:
        if any(id in system_data_items for id in data_item_ids):
            raise ForbiddenException("Forbidden to access requested data item(s)")
        return

    # Has application_id → check if this app is explicitly allowlisted
    allowed_ids = await get_allowed_system_data_item_ids(application_id)
    for data_item_id in data_item_ids:
        if data_item.status == SYSTEM and data_item_id not in allowed_ids:
            raise ForbiddenException("Forbidden to access requested data item(s)")

This is a per-application allowlist stored in the DB (application_to_allowed_data_item). So IDENTIFIER_TRANSLATION_CUSIP is only accessible to specific services explicitly granted permission — even if they have a valid internal token.

4API Design Concepts

Versioning Strategy

The API has three versions running simultaneously: v1, v2, v3. This is a common pattern — you can't change a public API without breaking existing callers, so you add a version instead of modifying.

web/api/router.py

api_router = APIRouter()
api_router.include_router(data_v1.router, tags=["data"])   # v1 routes
api_router.include_router(data_v2.router, tags=["data"])   # v2 routes
api_router.include_router(data_v3.router, tags=["data"])   # v3 routes

All three are registered at startup and run simultaneously. Older clients keep calling v1/v2; new clients use v3.

Why v3 was needed — two reasons:

  • Pagination model changed. V1/V2 page size counts data item values (fields), not rows. If you request 5 fields for 100 records, that's 500 values — a page_size of 1000 gives you 200 records. Confusing. V3 paginates by rows, which is what every caller actually wants. Changing V2's behavior would silently break existing callers.
  • New params field needed. Dataset-specific parameters (e.g. {"date": "2024-01-01"}) didn't exist in v2. Adding them to v2 would require updating every existing v2 caller's request schema.
# V3 schema extends V2 with only two changes:
class V3APIRequest(APIRequest):
    page_size: int = Field(100, ge=1)    # V2 default was 1000; V3 is 100
    params: dict[str, Any] | None = None  # new in V3

General principle: When you can extend without breaking, extend. When you must break, version. Never silently change behavior — callers built automated pipelines on V2's behavior; surprising them with a different page count would corrupt their data.

The Catalog Pattern

The catalog endpoint (GET /api/v1/dataset-catalog/) is a self-describing API — it tells callers what's available without them reading docs or source code.

// GET /api/v1/dataset-catalog/?dataset_type_name=INSTRUMENT
{
  "catalog_datasets": [{
    "dataset_type_id": 12,
    "dataset_type_name": "INSTRUMENT",
    "supported_identifiers": ["instrument_id", "entity_id"],
    "unique_identifiers": ["instrument_id"],
    "data_items": [
      {"data_item_id": 42, "data_item_name": "INSTRUMENT_NAME", "data_item_type": "Text"},
      {"data_item_id": 43, "data_item_name": "MATURITY_DATE", "data_item_type": "Date"}
    ]
  }]
}

This pattern is valuable when the set of available datasets/fields changes frequently — callers can discover what they can query at runtime rather than hardcoding field names. The public catalog automatically filters to only INTERNAL_EXTERNAL data items when is_public=True.

Pagination — Two Approaches

Pagination returns large result sets in pages. DAPI has two implementations, which is a good case study in trade-offs.

V1 / V2V3
What "page size" countsIndividual field valuesRows
Page size 100, 5 fields/row~20 rows100 rows
Multi-retriever supportYes (iterates retrievers)No (single dataset only)
Token format{retriever_idx}|{cursor} encodedOpaque base64 cursor

The page token is always opaque — clients treat it as a black box. Copy it from one response into the next request's page_token field. Internally it encodes enough state to resume the query exactly where it left off.

# Typical pagination loop (Python)
page_token = None
all_results = []

while True:
    resp = requests.post(url, json={
        "dataset_type_id": 11,
        "page_size": 100,
        **({"page_token": page_token} if page_token else {})
    }, headers=headers)

    data = resp.json()
    all_results.extend(data["results"])

    page_token = data.get("next_page_token")
    if not page_token:
        break

DE Analogy

Same concept as a database cursor — the cursor tracks "where we are" in the result set so the next query picks up from there. Identical to how you'd paginate through a Snowflake query result or use LIMIT/OFFSET in SQL, but cursor-based pagination is more efficient because it doesn't require re-scanning skipped rows.

Public vs Internal Surface Area

The same codebase serves both external clients (customers) and internal services (other Octus teams). Filtering happens at two layers:

Layer 1: Data item status

StatusWho can access
INTERNAL_EXTERNALEveryone — public and internal
INTERNALInternal tokens only
SYSTEMInternal + explicitly allowlisted apps only
DISABLEDNobody

Layer 2: Product grants

Even for INTERNAL_EXTERNAL fields, some datasets require a product grant in the token. INTEL_DATA is an example — the user's JWT must contain ProductGrant.INTEL_DATA (id=46), otherwise the retriever rejects the request. This lets the business grant/revoke access to data products without any code changes.

Layer 3: The public decorator

web/api/decorators.py

def validate_public_request_includes_auth(func):
    @functools.wraps(func)
    async def wrapper(*args, **kwargs):
        auth_ctx = kwargs.get("auth_ctx")
        # Public requests MUST have a valid token
        if auth_ctx and auth_ctx.is_public and auth_ctx.principal is None:
            raise DataApiException(status_code=401, message="Unauthorized")
        return await func(*args, **kwargs)
    return wrapper

Internal requests can technically work without a token (service-to-service calls that don't carry user context). Public requests always need one.

5The Factory Pattern

The Problem It Solves

DAPI serves 20+ datasets, each backed by a different database or service (Postgres, MySQL, Snowflake, an external API). The endpoint handlers don't need to know which database each dataset uses — they ask the factory for data and the factory figures out the rest.

Without the factory pattern, every endpoint would need this:

# Without factory — every endpoint needs a giant switch
if dataset_type_id == 11:
    result = await intel_retriever.fetch(request)
elif dataset_type_id == 12:
    result = await instrument_retriever.fetch(request)
elif dataset_type_id == 18:
    result = await carpo_retriever.fetch(request)
# ... 20 more elif blocks, updated every time a dataset is added

With the factory, every endpoint does this:

# With factory — completely decoupled from retriever implementations
retriever_factory = RetrieverFactory()
results = await retriever_factory.fetch_single(retriever_request)

How the Factory Resolves Retrievers

No big if/elif block. Instead: a database lookup to get a retriever name, then Python's getattr for dynamic dispatch.

Step 1: DB lookup

retriever/RetrieverFactory.py

retriever_name = name_map.get(data_item_id)   # e.g. "IntelDataRetriever" (string from DB)
retriever_class = getattr(data_api.retriever, retriever_name)   # the actual Python class

Step 2: Dynamic import via getattr

data_api/retriever/__init__.py imports all retriever classes, making them attributes of the data_api.retriever module. getattr(module, "IntelDataRetriever") returns the class object itself.

# data_api/retriever/__init__.py  (simplified)
from data_api.retriever.intel_data_retriever.intel_data_retriever import IntelDataRetriever
from data_api.retriever.deal_lens_retriever.deal_lens_retriever import DealLensRetriever
from data_api.retriever.carpo_data_retriever.carpo_data_retriever import CarpoDataRetriever
# ... all retrievers imported here — makes them accessible via getattr

Step 3: Instantiate and call

retriever = retriever_class()          # IntelDataRetriever()
result = await retriever.fetch(data_request)

Why this is elegant: Adding a new dataset means writing a retriever class, adding one import to __init__.py, and adding a DB row. Zero changes to the factory or endpoint handlers.

Codebase gotcha

The __init__.py import trick is why autoflake (the pre-commit linter) silently breaks things — it sees those imports as "unused" and strips them. Always commit __init__.py with --no-verify. See CLAUDE.md for the full workflow.

The Abstract Base Class Contract

Every retriever implements the same interface, defined by an abstract base class. The factory doesn't know or care what's inside IntelDataRetriever.fetch() — it just knows fetch() exists and returns a RetrieverOutput.

# data_api/retriever/DataRetriever.py  (simplified)
from abc import ABC, abstractmethod

class DataRetriever(ABC):
    retriever_identifier_types: set[IdentifierType]   # which identifier types it accepts

    @abstractmethod
    async def fetch(self, input: RetrieverInput) -> RetrieverOutput:
        ...   # every subclass must implement this

    async def validate_permissions(self, permissions: Permissions) -> None:
        pass   # default: no check; subclasses override when needed

This is the Strategy pattern: the algorithm (how to fetch intel data from Postgres) is encapsulated inside the strategy class (IntelDataRetriever), and the factory is the context that picks which strategy to use based on the request.

Putting It All Together

Trace one request end-to-end using everything above:

POST /api/v3/data/list
Authorization: Bearer <token>

{
  "ids": [{"value": "12345", "identifier_type": "entity_id"}],
  "data_item_names": ["ARTICLE_FULL_HTML"],
  "page_size": 10
}
1. Router matches path → calls get_data_v3() 2. Pydantic deserializes + validates JSON body → V3APIRequest object 3. Depends(resolve_auth) runs → validates JWT against Octus Auth SDK → returns AuthContext(is_public=True, product_grants=[46, ...]) 4. @validate_public_request_includes_auth decorator → is_public=True and principal exists → passes 5. @validate_public_data_item decorator → checks ARTICLE_FULL_HTML is INTERNAL_EXTERNAL status → passes 6. v3_api_request_to_retriever_input() → converts API request → RetrieverInput(is_public=True, product_grants=[46]) 7. RetrieverFactory.fetch_single() → resolves "ARTICLE_FULL_HTML" name → data_item_id 301 → looks up data_item_id 301 → retriever_name "IntelDataRetriever" → getattr(data_api.retriever, "IntelDataRetriever") → the class → IntelDataRetriever().validate_permissions() → checks ProductGrant.INTEL_DATA in product_grants → passes → IntelDataRetriever().fetch(retriever_input) → queries Postgres → returns rows 8. retriever_output_to_api_response() → converts rows → APIResponse 9. FastAPI serializes APIResponse → JSON → HTTP 200
